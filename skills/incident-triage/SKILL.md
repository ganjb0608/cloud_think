# 故障排查

这类任务每次形态都不一样，所以用软编排：你自己判断该查什么、派几个子 agent。

## 建议路径

1. **复现与定界**：先确认故障的触发条件和影响面，不要一上来就猜根因。
2. **并行取证**：日志、配置、最近变更，这三条线互不依赖，一次性派出去并行查。
3. **假设与验证**：对每个候选根因给出可证伪的验证方法，别停在"可能是网络问题"。
4. **修复方案**：给最小改动方案 + 回滚方案，标注风险。

## 约束

- 结论必须指向具体文件/配置/提交，不接受泛泛而谈。
- 区分「已证实」和「待验证」，不要把猜测写成结论。
- 子 agent 的取证结果要精炼带回，日志原文留在它自己的上下文里。
